# Maskey

Before changing UI code, MyGo usage, the MyGo version, or the build, read `.agents/skills/mygo-maintenance/SKILL.md`. `mygo install-skills` overwrites that directory, so put Maskey's own rules here, not there.

## Checks

```sh
golangci-lint run
go tool mygo vet .
go test -race ./...
```

Use the golangci-lint version that `.github/workflows/check.yml` pins; `.golangci.yml` owns the linters and the file-length limit. Split a file that outgrows the limit by concern within its package rather than raising the limit.

Tests use the in-memory backend in `internal/store/storetest`, the fake Bitwarden server in `internal/bitwarden/bitwardentest`, which has a cipher of its own so that it checks the client's, fake interpreters, a fake owner authentication, and an activity record in a temporary directory; those that start Apple's interpreter run only the helper's host check, helper code with Core Foundation and Security replaced by Python objects, or a bare socket client, and none makes a Keychain call. They cannot show live Keychain access, sync between Macs, the authentication dialog, the rendered window, or a request to Bitwarden.

## The real Keychain

The installed app, `mk`, and `keychain.New` with Apple's interpreter act on the user's iCloud Keychain, which syncs to every Mac on their Apple Account. Run them only with the user's authorization for that session, and then only on synthetic entries in a namespace made for the test, deleted at the end. Never list, read, or migrate entries you did not create; `mk doctor` reads every entry's attributes, so it is not a harmless probe either.

Inside a sandbox that blocks the `com.apple.securityd` Mach services, every direct Keychain call fails with OSStatus -25291 (kind `unavailable`), whatever the code under test does, and `mk` falls back to the Maskey service if it can reach its socket. Run live checks where the Keychain is reachable.

A Bitwarden store acts on the project its access token reaches, which other Macs share. Run against one only with a token the user supplied for a test project in that session, entered through the prompt or `--stdin` of `mk store add` or `mk store token`, never read or printed.

## Persistent identity

`store.Service` and `identifier` in `mygo.json` are the same string: the app's bundle identifier and the service attribute (`kSecAttrService`) of every entry. The account is `<namespace>/<NAME>`, the entry's kind is stored in `kSecAttrDescription` as a `store.ValueKind` string, its notes in `kSecAttrComment`, and its program access in `kSecAttrGeneric`, a JSON object whose `program_access` is `true`. Changing any of these, or the item's `synchronizable` flag, orphans or misreads existing entries on every synced Mac; it needs a migration the user has approved. A store other than `icloud` is a connection in `stores.json` beside the service's socket, named by an ID that never contains `:`, so that `store:namespace/NAME` stays unambiguous. Its access token and its entries' program access are items of the service `store.Service` + `.local` under the accounts `token/<id>` and `grants/<id>`, in the data protection keychain, not synchronizable and `ThisDeviceOnly`. A Bitwarden entry is the secret whose key is `<namespace>/<NAME>#<kind>`, its note the entry's notes; a key without a known kind is not an entry, and program access is granted to the secret's UUID. These need the same approved migration. `SetProgramAccess` takes the `store.Attributes.ID` that the listing before the owner's approval gave, so that an approval reaches no secret created under the name since; that identity stays in the process that listed and never crosses the socket.

Entries use `AfterFirstUnlock` so unattended jobs work while the screen is locked; `ThisDeviceOnly` classes cannot sync.

## Values

No path prints, logs, or returns a stored value outside `mk run` (into the child's environment, masked in its output; an entry of kind `ssh` gives the child only its public key and the signatures of an SSH agent that runs in `mk run`'s own process and ends with the command), `mk get` for an entry the owner granted program access, and the window's Reveal, Copy, and Edit form. Program access changes only after the owner authenticates, through the window's switch or through `mk grant` and `mk revoke`, which only the Maskey service carries out because it holds the command line's approval; do not add another path that changes it, a request field that claims an approval, or another get, export, or raw-output path. Values never travel in arguments, temporary files, error messages, or the activity record: `store.Error` carries none, and the helper's stderr stays unread because Python can quote the request there. The passphrase `mk set` asks for is a value too, though never stored, and so is a store's access token, which reaches the service from the prompt or stdin of `mk store add` and `mk store token` or from the Settings window and is kept only in its Keychain item. A Bitwarden store's snapshot holds values only sealed with the organization key. The record also leaves out notes, command arguments, and the environment, which can carry secrets.

Keep partial-value holdback strict in terminal mode too: a timed flush can expose a value written in pieces, even if it avoids a stalled terminal display.

## Keychain helper and service

`internal/keychain` runs the embedded helper as `/usr/bin/python3 -I -S -c` with only `PATH` in its environment, the request on stdin. The absolute path and the bare environment keep another interpreter, or `DEVELOPER_DIR` redirecting Apple's shim, from hosting it without Apple's `com.apple.python3` identity. The ready line printed after the host check is what separates a confirmed failure (`prerequisite`) from a write that may have happened (`uncertain`); keep both outcomes distinct.

`internal/agent` is the per-user Maskey service for sandboxed callers and for every grant and revoke. Through 0.0.10 it was the Keychain service, under the job `io.github.entwining.maskey.keychain`, the argument `--keychain-service`, and `keychain.sock`; `legacy_darwin.go` removes that job and its files on install and uninstall, and `main` installs the present service when launchd starts a build with the earlier argument. A client whose process cannot write the activity record sends each recorded operation to the service first, which performs and records it, so a sandbox never needs write access to the record; otherwise the client uses the Keychain directly first. Either way it switches to the other side only on `unavailable`, never on `locked`, `cancelled`, or `uncertain`, and stays there for the rest of the process. Once a write is sent, only the service's answer settles it: a cancelled client withdraws a grant or revoke with a `{"cancel":true}` frame and waits for the answer, and the service cancels only the owner's approval, never a write the owner approved. A connection that ends without an answer is `uncertain`, not a reason to resend. Both peers authenticate as the same signed executable before a request crosses the socket. Only the service reaches a remote store: it holds the token and the session, writes the snapshot, and changes `stores.json`, so `mk` and the window use `agent.NewRemote` for one, with no direct side to fall back to. A client is made for a `stores.Connection`, not a name: each of its requests carries that connection's `Target`, and `Registry.Backend` refuses with `conflict` a request whose name now means another connection, so do not add a way to open a remote store by name alone. A process that may not read `stores.json` (`stores.ErrDenied`), as in a sandbox, has the service read it with `Client.Stores`; when that fails too, the command fails rather than work as if this Mac had only iCloud Keychain. `Registry` holds one connection's turn across its requests to Bitwarden, and its own lock only around the table of backends and `stores.json`, so a slow store holds back no other; make no network request under that lock. `Registry.Remove` removes the token first and the name in `stores.json` last, so that a removal that stopped partway can be repeated. Writes go to Bitwarden first and never queue; a read uses the snapshot while it is fresh or Bitwarden cannot be reached, a listing marked `store.WithSaved` uses it whatever its age, which is how the window shows a store before Bitwarden answers, and a refused token discards it. The window marks its requests (`agent.NewWindowRemote`), which the service trusts because peers are the same executable: it records them with the window as the caller, keeps the owner's approval of their program access changes apart from `mk`'s, and performs a read for `reveal`, `copy`, or `edit` only for them and only for a remote store, since the window reads iCloud Keychain itself. Each command works on one store. The window lists every store of this Mac together and names an entry by its store and reference (`entryID`), so each of its actions opens that entry's store. Add no lookup that falls through to another store.

The service performs only Keychain operations, a remote store's requests, and the owner's authentication for program access; the command and its masking stay in the caller's sandbox.

An operation on an entry is recorded once, by the process that ends it. `store.Recorded` wraps the backend there, around the Keychain in the window and in `agent.New` for `mk`, and around every backend the service dispatches to, and the Keychain and Bitwarden backends record nothing themselves; a new `store.Backend` method does not compile until `recorded` says whether it is recorded. A direct attempt that ends `unavailable` is not recorded when the service performs the operation instead (`store.WithFallback`), nor is the add of a replacement that finds the entry (`store.WithReplacing`). What reaches no backend is recorded by who ends it: `Store.ChangeAccess` a refused approval or a store it could not list, and `recordUnperformed` in `internal/agent` an operation that neither the Keychain nor the service received or whose store the service could not open; a request the service received is the service's to record, also when its answer is lost. Nothing else records. `main`, the service once it authenticates a client, and the window describe their caller with `activity.WithCaller` before any operation, while that program still runs.

## Command line and GUI in one executable

`main` dispatches to the CLI, and to the hidden `--run-monitor` that `mk run` starts on a terminal, before any GUI work. Nothing on a CLI path may call `mygo.App` or `mygo.NewWindow`, because they create the GUI backend; `mk` reads its version from the embedded `mygo.json` for that reason. The error kinds, exit statuses, and output streams are a contract that agents script against: the command definitions in `internal/cli` and its `exit-codes` help topic own it. Give an error a recovery where one helps. A hint or warning message is a lowercase fragment without a final period, its steps joined by ";" or ", then". Agents learn the workflow from `resources/skills/maskey/SKILL.md`, which ships in the app; change it with the commands it describes.

`uninstall` in `internal/cli/uninstall.go` is the one list of what Maskey and MyGo write under the home directory, except the Maskey service's files, which `serviceFiles` in `internal/agent/uninstall_darwin.go` lists and `RemoveService` removes under the lock `install` takes, keeping what a job that could not be stopped still writes (`ServiceItem.MayRun`), the earlier Keychain service's included: code that starts writing there adds the path to the matching list and to `TestUninstall` or `TestRemoveServiceUndoesInstall`, and `TestHomePathFiles` fails on a file that derives a home path without being listed. That scan covers only this module, so a MyGo upgrade compares MyGo's `paths.go` and the plugins the app uses with the list.

## Release builds

The production build must not contain MyGo's automation plugin. For native GUI checks, build a scratch copy with a `//go:build e2e` file that imports `github.com/egoist/mygo/plugins/automation`, with `GOFLAGS=-tags=e2e` and `MYGO_INSPECTOR=1`, without which `mygo build` leaves the plugin out; never add that import to the module. Confirm that `strings` finds no `plugins/automation` in the built executable: `mygo build` strips the symbol table, so `go tool nm` shows no symbol either way. The automation tree of a window covered by other windows is stale, because MyGo builds no frames for it; a `capture` request builds one.

Installed apps update themselves from the latest GitHub Release, accepting only archives signed with the MyGo update key whose public half is `updates.publicKey` in `mygo.json`. Losing that key strands every installed copy, and replacing it needs a release signed with the old one; never read, print, or commit it. Builds without the key, such as Check and local builds, skip the update files.

Pushing a tag `v<version>` runs the Publish workflow, which requires the tag to match the version in `mygo.json` and a `## <version>` section in `CHANGELOG.md` (the update window's release notes), reruns Check, signs the update with the `MYGO_UPDATER_PRIVATE_KEY` secret, attests the archive, and publishes every file through a draft so apps never read a manifest whose archive is missing. The app is signed ad hoc, so user-facing install steps must cover Gatekeeper's quarantine, which Homebrew applies to each version it installs.

After changing an action reference or adding a workflow, regenerate `.github/workflows/actions.lock` with `gh actions-lock`; the Validate actions lock workflow fails on a stale or missing entry. Renovate updates actions together with the lock and holds MyGo upgrades for review, as `.github/renovate.json` explains.
