# Maskey

Before changing UI code, MyGo usage, the MyGo version, or the build, read `.agents/skills/mygo-maintenance/SKILL.md`. `mygo install-skills` replaces MyGo's bundled files. Keep Maskey's own rules here.

## Checks

```sh
golangci-lint run
go tool mygo vet .
go test -race ./...
```

Use the golangci-lint version that `.github/workflows/check.yml` pins; `.golangci.yml` owns the linters and the file-length limit. Split a file that outgrows the limit by concern within its package rather than raising the limit.

Repository tests use synthetic stores and owner approval. Tests that start Apple's interpreter exercise the host check, stubbed helper, or socket client without making a Keychain call. They cannot show live Keychain access, sync between Macs, the authentication dialog, the rendered window, or a request to a live Bitwarden project.

## The real Keychain

The installed app, `mk`, and `keychain.New` with Apple's interpreter can act on the user's iCloud Keychain. Changes reach the other Macs syncing it. Run them only with the user's authorization for that session, and then only on synthetic entries in a namespace made for the test, deleted at the end. Never list, read, or migrate entries you did not create; `mk doctor` reads every iCloud entry's attributes and refreshes each configured Bitwarden store, so it is not a harmless probe either.

Inside a sandbox that blocks the `com.apple.securityd` Mach services, every direct Keychain call fails with OSStatus -25291 (kind `unavailable`), whatever the code under test does, and `mk` falls back to the Maskey service if it can reach its socket. Run live checks where the Keychain is reachable.

A Bitwarden store acts on the project its access token reaches, which other Macs share. Run against one only with a token the user supplied for a test project in that session, entered through the prompt or `--stdin` of `mk store add` or `mk store token`, never read or printed.

## Persistent identity

`store.Service` and `identifier` in `mygo.json` are the same string: the app's bundle identifier and the service attribute (`kSecAttrService`) of every iCloud entry. The account is `<namespace>/<NAME>`, the entry's kind is stored in `kSecAttrDescription` as a `store.ValueKind` string, its notes in `kSecAttrComment`, and its program access in `kSecAttrGeneric`, a JSON object that grants access only when `program_access` is `true`. Changing any of these, or the item's `synchronizable` flag, orphans or misreads existing entries on every synced Mac; it needs a migration the user has approved. A store other than `icloud` is a connection in `stores.json` beside the service's socket, named by an ID that never contains `:`, so that `store:namespace/NAME` stays unambiguous. Its access token and its entries' program access are items of the service `store.Service` + `.local` under the accounts `token/<id>` and `grants/<id>`, in the data protection keychain, not synchronizable and `ThisDeviceOnly`. A Bitwarden entry is the secret whose key is `<namespace>/<NAME>#<kind>`, its note the entry's notes; a key without a known kind is not an entry, and program access is granted to the secret's UUID. These need the same approved migration. `SetProgramAccess` takes the `store.Attributes.ID` that the listing before the owner's approval gave, so that an approval reaches no secret created under the name since; that identity stays in the process that listed and never crosses the socket.

Entries use `AfterFirstUnlock` so unattended jobs work while the screen is locked; `ThisDeviceOnly` classes cannot sync.

## Values

No path prints, logs, or returns a stored value outside `mk run` (into the child's environment, masked in its output; an entry of kind `ssh` gives the child only its public key and the signatures of an SSH agent that runs in `mk run`'s own process and ends with the command), `mk get` for an entry the owner granted program access, and the window's Reveal, Copy, and Edit form. Program access changes only after the owner authenticates, through the window's switch or through `mk grant` and `mk revoke`, which only the Maskey service carries out because it holds the command line's approval; do not add another path that changes it, a request field that claims an approval, or another get, export, or raw-output path. Values never travel in arguments, temporary files, error messages, or the activity record: `store.Error` carries none, and the helper's stderr stays unread because Python can quote the request there. The passphrase `mk set` asks for is a value too, though never stored, and so is a store's access token, which reaches the service from the prompt or stdin of `mk store add` and `mk store token` or from the Settings window and is kept only in its Keychain item. A Bitwarden store filters the project's key index before fetching values and notes. Its snapshot holds only Maskey entries and is sealed with the organization key before writing to disk. The record also leaves out notes, command arguments, and the environment, which can carry secrets.

Keep partial-value holdback strict in terminal mode too: a timed flush can expose a value written in pieces, even if it avoids a stalled terminal display.

## Keychain helper and service

`internal/keychain` runs the embedded helper as `/usr/bin/python3 -I -S -c` with only `PATH` in its environment, the request on stdin. The absolute path and the bare environment keep another interpreter, or `DEVELOPER_DIR` redirecting Apple's shim, from hosting it without Apple's `com.apple.python3` identity. The ready line printed after the host check is what separates a confirmed failure (`prerequisite`) from a write that may have happened (`uncertain`); keep both outcomes distinct.

`internal/agent` handles CLI grants and revokes and the window's remote grants and revokes. The window approves iCloud changes locally. Keep the launchd migration in install, uninstall, and the `agent.LegacyArg` entry point. For iCloud operations with a direct path, the client prefers the service when the operation is recorded and the client cannot write the activity record. Otherwise it prefers the Keychain. Only `unavailable` permits fallback. Later calls skip a side already found unavailable. Once a write is sent, only the service's answer settles it: a cancelled client withdraws a grant or revoke with a `{"cancel":true}` frame and waits for the answer. Until the owner approves, the withdrawal, the service's stop, and the time limit of other remote requests end a grant or revoke, also while it opens or lists its store; nothing ends the writes the owner approved. If a write may have been sent, a lost answer is `uncertain` and must not trigger a resend. Both peers authenticate as the same signed executable before a request crosses the socket.

Only the service reaches a remote store. It holds the token and session, writes the snapshot, and changes `stores.json`. Both CLI and window remote clients have no direct fallback. A client is made for a `stores.Connection`, not a name: each of its requests carries that connection's `Target`, and `Registry.Backend` refuses with `conflict` a request whose name now means another connection, so do not add a way to open a remote store by name alone. A request about a store itself (`store_remove`, `store_token`) carries the `Target` its caller resolved before it asked the owner, as a confirmation, a prompt, or a dialog does, and none when the command only names the store (`--yes`, `--stdin`). A process that may not read `stores.json` (`stores.ErrDenied`), as in a sandbox, has the service read it with `Client.Stores`; if that fails, only an explicitly selected `icloud` can be resolved without the configuration.

The service serves each connection in its own goroutine and limits only how many it serves at once (`connectionLimit`); gate no request on a smaller shared pool, which requests stuck in one slow store would fill. `Registry` holds one connection's turn across its requests to Bitwarden, and its own lock only around the table of backends and `stores.json`. A `bitwarden.Backend` lets one exchange with Bitwarden at a time run under the connection's exchange turn, a turn apart from the registry's that `Registry` keeps for each name and passes to every backend it makes, so that a backend made after a removal or new token closed another waits for the exchange that one is still in. The backend guards its snapshot, grants, and closed state with a state lock, so that a read its snapshot answers, and `Close`, wait for no exchange. Make no request to Bitwarden under the registry's lock or a backend's state lock, and wait for no turn while holding either. A wait for a turn (`bitwarden.Turn`) follows the request's context, and a request that gives up has done nothing. `Close` does not wait for Bitwarden: an exchange that ends after it installs nothing, writing neither snapshot nor grants, and a write still reports its outcome. `Registry.Remove` removes the token first and the name in `stores.json` last, so that a removal that stopped partway can be repeated. Changes to Bitwarden secrets require a live write and never queue. Program access stays local. Ordinary reads can reuse a fresh snapshot or an older one on network, rate-limit, or server errors. The window requests `store.WithSaved` for its initial listing regardless of age. Discard the cached view when Bitwarden refuses authentication or read access, or the project is missing.

The window marks its requests (`agent.NewWindowRemote`), which the service trusts because peers are the same executable: it records them with the window as the caller, keeps the owner's approval of their program access changes apart from `mk`'s, and performs a read for `reveal`, `copy`, or `edit` only for them and only for a remote store, since the window reads iCloud Keychain itself. Each entry command works on one store. The window lists every store of this Mac together and names an entry by its store and reference (`entryID`), so each of its actions opens that entry's store. Add no lookup that falls through to another store.

The service performs only Keychain operations, a remote store's requests, changes to `stores.json`, and the owner's authentication for program access; the command and its output masking stay in the caller's sandbox.

Give each recordable entry operation one recording owner. Wrap the backend where the operation ends with `store.Recorded`. A direct attempt that ends `unavailable` is not recorded when the service performs the operation instead (`store.WithFallback`), nor is the add of a replacement that finds the entry (`store.WithReplacing`). `Store.ChangeAccess` records a refused approval or a failed listing. The client records a recordable request that neither side received if it can write the record. Once the service receives a request, it owns the record even if it cannot open the store or its answer is lost. `main`, the service once it authenticates a client, and the window describe their caller with `activity.WithCaller` before any operation, while that program still runs.

## Command line and GUI in one executable

`main` dispatches to the CLI, and to the hidden `--run-monitor` that `mk run` starts on a terminal, before any GUI work. Nothing on a CLI path may call `mygo.App` or `mygo.NewWindow`, because they create the GUI backend; `mk` reads its version from the embedded `mygo.json` for that reason. The error kinds, exit statuses, and output streams are a contract that agents script against: the command definitions in `internal/cli` and its `exit-codes` help topic own it. Give an error a recovery where one helps. A hint or warning message is a lowercase fragment without a final period, its steps joined by ";" or ", then". Agents learn the workflow from `resources/skills/maskey/SKILL.md`, which ships in the app; change it with the commands it describes.

Add new home-directory artifacts to the cleanup in `internal/cli/uninstall.go` or, for service files, `internal/agent/uninstall_darwin.go`. Cover them in `TestUninstall` or `TestRemoveServiceUndoesInstall`. `RemoveService` shares the install lock. Preserve files a current or legacy job may still write (`ServiceItem.MayRun`). `TestHomePathFiles` scans this module for known home-path patterns, so a MyGo upgrade compares MyGo's `paths.go` and the plugins the app uses with the list.

## Release builds

The production build must not contain MyGo's automation plugin. For native GUI checks, build a scratch copy with a `//go:build e2e` file that imports `github.com/egoist/mygo/plugins/automation`, with `GOFLAGS=-tags=e2e` and `MYGO_INSPECTOR=1`, without which `mygo build` leaves the plugin out; never add that import to the module. Confirm that `strings` finds no `plugins/automation` in the production executable. `mygo build` strips the symbol table, so `go tool nm` shows no symbol either way.

Installed apps update themselves from the latest GitHub Release, accepting only archives signed with the MyGo update key whose public half is `updates.publicKey` in `mygo.json`. Losing that key strands every installed copy, and replacing it needs a release signed with the old one; never read, print, or commit it. Builds without the key, such as Check and local builds, skip the update files.

Pushing `v<version>` publishes an update for installed copies and notifies the Homebrew tap. Match the tag to `mygo.json` and the `## <version>` release notes in `CHANGELOG.md`. Keep the release in draft until all files are present so the published manifest always has its archive. The app is signed ad hoc, so user-facing install steps must cover Gatekeeper's quarantine, which Homebrew applies to each version it installs.

After changing an action reference or adding a workflow, regenerate `.github/workflows/actions.lock` with `gh actions-lock`; the Validate actions lock workflow fails on a stale or missing entry.
